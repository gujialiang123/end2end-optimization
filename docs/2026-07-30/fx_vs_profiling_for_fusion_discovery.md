# FX graph 还是 profiling？—— 给 agent 设计融合机会发现流程

**日期**：2026-07-30
**问题**：如果目标是让 agent 自动找 kernel fusion 机会，
应该从 torch.compile 的 FX graph 出发，还是像我们之前那样从 profiling 结果出发？

**回答方式**：用我们自己做过的 5 个案例做交叉分类，看每种方法**分别会漏掉什么**。
不做泛泛的「两个都重要」式回答。

---

## 0. 结论先行

**两者回答的不是同一个问题，而且各自的失败模式我们都亲身踩过：**

| | FX graph | profiling |
|---|---|---|
| 看到的是 | **结构**（代码写成什么样） | **执行**（这次实际跑了什么） |
| 典型错误 | **过度生成**：报告不执行的路径 | **过度自信**：把某个配置下的现象当普遍事实 |
| 我们踩过的坑 | （下面 §2 实测） | **OLMo-2 高估 10 倍**（关 CUDA graph 才存在的开销） |
| 成本 | 秒级，不占 GPU | 分钟级，独占 GPU |
| 能否量化收益 | ❌ 不能 | ✅ 能 |

**给 agent 的答案：FX 做候选生成（廉价、高召回），profiling 做验证（昂贵、是 ground truth），
两者之间必须有一道「这条路径在生产配置下真的执行吗」的闸门。**

**那道闸门是我们花了最大代价才学到的东西，也是这套流程里最容易被忽略的一环。**

---

## 1. 用五个真实案例做交叉分类

| # | 案例 | 端到端收益 | FX 能找到吗 | profiling 能找到吗 |
|---|---|---|---|---|
| 1 | **Gemma-3 q_norm/k_norm 未融合** | +36.6% / +24.5% | ✅ 能（图上是展开的 pow→mean→rsqrt 链） | ✅ 能（占 kernel 时间 46.3%） |
| 2 | **LFM2.5 residual 未融合** | +6.57%（七项） | ✅ 能（add 紧跟 rms_norm 的模式） | ✅ 能（48 个独立 add kernel） |
| 3 | **LFM2.5 MoE config 缺失** | +23.3% | ❌ **完全看不到** | ⚠️ 间接（要查文件是否存在） |
| 4 | **OLMo-2 qk_norm eager 回退** | prefill +14.5%，decode ≈0 | ⚠️ **会误报**（见 §2） | ⚠️ **高估 10 倍**（见 §3） |
| 5 | **LFM2.5 gate+idx** | **不显著** | ✅ 能找到（结构上确实没融合） | ✅ 能测到 kernel 级 1~2% | 

**读这张表的要点不是「谁赢」，而是三件事：**

- **案例 3**：config 缺失是**运行时查表**的问题，根本不在计算图里。FX 结构上不可能发现。
- **案例 4**：**两种方法都出错了**，而且错的方向不同。
- **案例 5**：两种方法**都会报告它**，但它端到端不显著——说明**发现机制之外还必须有验证环节**。

---

## 2. FX 的失败模式：只能看到 trace 那一刻走的那条路

OLMo-2 的真实结构是：

```python
if self.alt_stream is not None and get_is_capture_mode():
    q = self.q_norm(q.reshape(-1, q_shape[-1]))   # 融合路径
else:
    q = self.q_norm.forward_native(q)             # eager 路径
```

复刻这个结构做实测：

```
capture_mode=False -> trace 到 6 个算子: 展开的 eager 链（会被判定为"有融合机会"）
capture_mode=True  -> trace 到 1 个算子: 已融合（无机会）
```

**同一个模型，trace 时的运行时状态不同，FX 给出完全相反的结论。**

而 OLMo-2 的生产真相是：`alt_stream` 在 CUDA 上恒非 None，**CUDA graph 捕获时走的就是融合路径**，
稳态 decode 回放的图里根本没有 eager kernel。

**所以如果 agent 只信 FX，会报告一个在生产中根本不执行的"机会"。**

这不是假想——**我们的 profiling 审计就是在这里高估了 10 倍**（下一节）。
FX 会犯同一个错误，只是原因不同（一个是 trace 时机，一个是 profiling 配置）。

---

## 3. profiling 的失败模式：测量配置 ≠ 生产配置

我们的审计工具默认加 `--disable-cuda-graph`（为了让 kernel 归因干净）。
在 OLMo-2 上得到：

| 阶段 | 缺口 | cuda_graph=OFF | cuda_graph=ON |
|---|---|---:|---:|
| decode | eager_norm_decomp | 3.88% | **消失** |
| decode | eager_norm_rsqrt | 2.17% | **消失** |
| decode | eager_norm_pow | 1.66% | **消失** |
| | *小计* | *7.71%* | **0** |
| prefill | eager_norm_decomp | 7.93% | 7.91%（不变） |

**审计报 7.71%，端到端只有 +0.45%。** 因为那个开销只在关掉 CUDA graph 时存在。

**教训**：profiling 是 ground truth，但**只对它实际运行的那个配置成立**。
「为了测量而改变配置」这件事本身可能改变被测对象。

## 4. 两种方法的成本-召回对比

| | FX graph | profiling |
|---|---|---|
| 一个模型的成本 | **秒级**，CPU 即可 | **10+ 分钟**，独占 GPU |
| 扫 11 个模型 | 几分钟 | 几小时 |
| 输出 | 「这里结构上没融合」 | 「这里占了 X% kernel 时间」 |
| 能否排序优先级 | ❌ 不能（不知道热不热） | ✅ 能 |
| 能否证明收益 | ❌ 不能 | ⚠️ 只能给上界 |
| 唯一能证明收益的 | — | **端到端 A/B** |

★ **注意最后两行的区别**：即使是 profiling 给的 `% kernel time` 也**只是上界**，
不是可实现收益。我们的次可加性发现证明了这点——
LFM2.5 上各组件单独收益之和 12.80%，一起测只有 6.21%，**兑现率 0.49**。

**所以任何自动发现流程，末端都必须挂一个端到端 A/B，没有例外。**

## 5. 给 agent 的建议流程

```
┌─ 阶段 1：静态扫描（秒级，不占 GPU，高召回低精度）
│   • FX graph 上匹配未融合的算子链
│   • 同时做「已有融合原语但调用点没接上」的签名扫描  ← 我们命中率最高的一条
│   • 输出：候选列表（预期大量误报，这没关系）
│
├─ 阶段 2：执行确认（关键闸门，最容易被跳过）★
│   • 这条路径在生产配置下真的执行吗？
│   • 具体做法：装分支计数器 / 查 CUDA graph 捕获产物 / 查编译缓存
│   • 我们的经验：这一步能砍掉 OLMo-2 那类误报
│
├─ 阶段 3：profiling 定量（分钟级，占 GPU）
│   • 在**生产配置**下测（CUDA graph 开着！）
│   • 输出：占 kernel 时间的百分比 = 收益上界
│   • 只对通过阶段 2 的候选做
│
└─ 阶段 4：端到端 A/B（唯一算数的证据）
    • 多次重复 + 统计检验 + 顺序对照
    • 组合优化必须整体测（次可加性）
```

### 为什么阶段 2 是关键

这是我们**用两次失败换来的**：

- **OLMo-2**：审计说 7.71%，实测 +0.45%，因为 profiling 关了 CUDA graph
- **Triton 3.6**：得出「编译器升级吃掉了 tuning 收益」，实为**基线加载了我们自己的 config**

两次都是「测量对象不是我以为的那个」。第二次尤其值得记：
**结果符合预期时，警惕性最低。**

阶段 2 的通用形式是：**别信声明，去查执行产物。**
- CUDA graph 捕获了什么 → 查 capture 日志 / 装计数器
- 实际编译了哪个 kernel → 查 Triton 缓存里的 `.ttgir`（我们靠这个发现了 BK=32 从未编译）
- 实际加载了哪个 config → 断言而不是假设（现已固化为 `assert_clean_baseline()`）

## 6. 直接回答：哪个更合适

**如果只能选一个，选 profiling。**

理由是**案例 3**（MoE config，+23.3%，我们最大的单项收益之一）
**FX 结构上不可能发现**——它不在计算图里，是运行时查表未命中。

而 FX 能找到的（案例 1、2），profiling 也都能找到。

**但真实答案是：FX 用来做 profiling 够不到的那件事——扫描广度。**

| | FX 的不可替代之处 |
|---|---|
| 成本 | 扫 100 个模型 = 几分钟；profiling 要几天 |
| 覆盖 | 能看到**没被执行到的路径**（冷门分支、少见 shape）|
| 精确性 | 数据依赖是精确的（`num_users` 直接给出融合安全性）|

**所以对 agent 来说，正确问法不是「二选一」，而是「谁做漏斗的哪一层」：**

> **FX 做第一层漏斗（廉价、扫得广、可以有误报），
> profiling 做第二层（贵、但能排序），
> 端到端 A/B 做第三层（最贵、但唯一算数）。**
>
> **而漏斗之间必须插入「这条路径真的执行吗」的闸门——
> 这是我们花最大代价学到的，也是现成工具都不提供的一环。**

## 7. 我们相对别人的优势在哪

做这个方向的团队不少，但我们手上有一样别人多半没有的东西：

**11 个模型的人工审计基线**（`docs/2026-07-28/cross_architecture_audit.md`），
以及 5 个已完成端到端验证的案例（含 2 个负面结果）。

这意味着我们能做一件别人做不了的实验：

> **把自动发现流程跑在这 11 个模型上，和人工结果逐一对比，
> 算出真实的召回率和误报率。**

没有人工基线，就只能说「我的 pass 找到了 N 个机会」，
无法回答「漏了多少」「其中几个是真的」。

**这个基线本身就是我们最值钱的资产之一。**
