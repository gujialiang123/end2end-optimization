# 撤回：Triton 3.6 的实验因基线污染而无效

**日期**：2026-07-29 · **状态**：⚠️ **本文撤回 `triton_36_retune_findings.md` 的主要结论**

---

## 一句话

**我在 Triton 3.6 上测的"默认基线"，实际加载的是我自己 tune 的那个 config。**
所以"3.6 让 tuning 收益归零"这个结论**没有证据支持**——真正的 3.6 默认路径我从未测过。

---

## 错在哪

3.6 的 sweep 和端到端都用了 `PYTHONPATH=/tmp/sglang_lfm/python`。
而 `/tmp/sglang_lfm` 是**我为 PR #32687 建的分支 worktree，里面就放着待测的那个 config 文件**：

```
/tmp/sglang_lfm/python/sglang/srt/layers/moe/moe_runner/triton_utils/
    configs/triton_3_5_1/E=32,N=1792,device_name=NVIDIA_H200.json   ← 22:23 提交
```

sweep 是 04:48 跑的，文件早就在那。

在 Triton 3.6 下，`get_moe_configs` 先找 `triton_3_6_0/` —— 没有 —— 然后**跨版本回退**，
正好找到 `triton_3_5_1/` 目录里我的文件并加载。

于是"无 config 的默认启发式"这个基线，实际上是**已经 tune 过的 config**。

## 证据链

**1. 编译产物里根本没有默认配置的 kernel。**
默认配置是 `BM=64, BN=64, BK=32`。扫遍所有 Triton 编译缓存：

| 缓存 | BK=32（即默认配置）的 kernel 数 |
|---|---:|
| 3.5.1 sweep（`~/.triton/cache`） | **10** ✓ |
| 3.6 sweep（`/tmp/triton_cache_gpu{0,3,6,7}`） | **0** ✗ |

3.6 的四张卡加起来编译了 8000+ 个 kernel，**没有一个是 BK=32**。默认路径从未被执行。

**2. 数字能被精确分解，5/5 完全吻合。**

若"3.6 default" = 我的 tuned config 在 3.6 上跑，则应有：

```
(3.5.1默认 / "3.6默认")  ==  (3.5.1 上 tuning 的增益) × (同一 config 在 3.6 上的增益)
```

| M | 观测比值 | tuning 增益 | 同 config 版本增益 | 乘积 | 吻合 |
|---:|---:|---:|---:|---:|:--:|
| 24 | 1.107× | 1.078× | 1.027× | 1.107× | ✓ |
| 48 | 1.314× | 1.372× | 0.958× | 1.314× | ✓ |
| 96 | 1.409× | 1.391× | 1.013× | 1.409× | ✓ |
| 1536 | 1.606× | 1.561× | 1.028× | 1.606× | ✓ |
| 3072 | 1.699× | 1.626× | 1.045× | 1.699× | ✓ |

**没有任何剩余项。** 所谓"3.6 默认路径快 1.4–1.7×"，完全等于
「tuning 本来的收益」×「同一 config 在 3.6 上的 1.04× 小幅提升」。

**3. 端到端的两个 arm 跑的是同一个 config。**
`default` arm 不设 `SGLANG_MOE_CONFIG_DIR` → 读包内 configs → 还是我的文件；
`cfg35on36` arm 显式指向我的文件。**两臂相同**，所以 0.997× 是纯噪声，
不是"config 在 3.6 上没用"。

## 哪些结论作废，哪些仍然成立

### ❌ 作废

| 原结论 | 为什么不成立 |
|---|---|
| 「Triton 3.6 默认路径 +29.8%，比 tuning 还快」 | 那个"默认"是 tuned config |
| 「3.6 上 0/19 桶达标，tuning 空间归零」 | 基线本来就是 tuned config，当然没东西能超过它 1.15× |
| 「3.6 的 default 比 3.5.1 的 tuned 快 5.2%」 | 是同一个 config 自己比自己，1.04× |
| 「3.6 改进了 BK=32 的代码生成」 | 建立在同一个错误之上；BK=32 从未在 3.6 上跑过 |
| 「优化机会有保质期 / 升级依赖优先于手工优化」 | **推理本身合理，但这个案例不构成证据** |

### ✅ 仍然成立（这些用的是干净的 3.5.1 基线）

| 结论 | 证据 |
|---|---|
| **这个 shape 在 H200 上没有 config，走两档启发式** | 文件在所有 `triton_*` 目录下都不存在，已实测 |
| **3.5.1 上 tuning 值 1.37–1.74×（kernel）** | 真默认基线，缓存里有 10 个 BK=32 kernel 为证 |
| **3.5.1 上端到端 +23.3%，8/8 不重叠** | `lfm25_prcand`，未被污染 |
| **decode 中性（counterbalanced 后 p=0.079）** | 同上 |
| **同一 config 在 3.6 上快约 1.04×** | 822/894 个 config 逐一配对，与污染无关 |

**PR #32687 的所有主张不受影响**——它只引用 3.5.1 的数字，而那批测量是干净的。

## 根因与防范

**根因**：拿"包含待测产物的分支"当实验的源码树。
config 文件是**数据**不是代码，它藏在 package 目录里，不像 monkeypatch 那样显眼，
而 `get_moe_configs` 的跨版本回退又让它在一个**本不该匹配的 Triton 版本**下被悄悄加载。

**为什么没有当场发现**：结果"很合理"——升级编译器带来提升，符合直觉，
所以我没有质疑它。**一个符合预期的结果比一个异常结果更危险**。

**真正戳破它的**：不是复查流程，而是用户追问机制（"具体改了什么代码生成？"）。
为了回答，我去翻编译产物，才发现 BK=32 的 kernel 根本不存在。

### 三条可执行的防范

1. **实验的源码树必须与产物树分离。** 待测 artifact 不能放在实验读取的 `PYTHONPATH` 里。
2. **基线必须自证。** 每次 A/B 都要断言基线真的是基线——
   本例只需在 sweep 开始时打印 `get_moe_configs(...)` 是否返回 `None`，一行就能挡住。
3. **拿编译产物交叉验证。** Triton 缓存里的 `.ttgir` 记录了**实际执行的** BLOCK 参数，
   这是比任何日志都硬的证据。`grep` 一下 tile 形状就知道跑的是不是你以为的配置。

### 已落地的修复

`rk_microbench.py` 现在会在 sweep 开始时检查并打印基线的真实来源，
基线不是"无 config"时**直接报错退出**（见 `assert_clean_baseline`）。
